Fundamentals of Accelerated Data Science

Concepts behind the notebooks

A notebook-by-notebook guide to the ideas that matter: how GPU acceleration changes data workflows, how RAPIDS libraries connect, and how the course moves from data preparation to graphs, machine learning, deployment, and an integrated application.

28 notebooks · Source: the notebooks directly inside the fundamentals folder · Conceptual summary, not a code or answer key

Section 1

Accelerated data processing

The governing idea is to express work as column-wise, vectorized operations, keep data on the GPU, and manage memory and data movement deliberately.

1-00_introduction.ipynbEnvironment and GPU workflow
  • JupyterLab combines notebooks, files, terminals, and independent kernels in one interactive environment.
  • nvidia-smi reveals GPU availability, memory use, and active processes; leaving headroom matters because operations can create temporary allocations.
  • %time and %%time support empirical performance comparison.
  • Each notebook has its own kernel, so shutting down unused kernels releases GPU memory across the session.

Core takeaway: acceleration starts with observing the hardware and controlling the execution environment.

1-01_section_overview.ipynbThe data-processing pipeline
  • The section follows a coherent pipeline: manipulate data, manage memory, exchange data among libraries, group and visualize it, then build ETL and scalable workflows.
  • Prepared data becomes the foundation for the graph and machine-learning sections.

Core takeaway: end-to-end throughput matters more than accelerating one isolated operation.

1-02_data_manipulation.ipynbDataFrames, vectorization, and cuDF
  • cuDF provides a pandas-like DataFrame API for loading, selecting, filtering, joining, aggregating, and transforming data on a GPU.
  • DataFrames are two-dimensional labeled structures; Series are one-dimensional labeled arrays. Index alignment preserves row correspondence during operations.
  • Column operations, scalar broadcasting, boolean masks, and reductions expose parallelism; row-by-row iteration works against GPU architecture.
  • .loc supports label-based selection, while .map() and .apply() cover logic that cannot be expressed with built-in vector operations.
  • cudf.pandas can accelerate compatible pandas code and fall back to CPU for unsupported operations.

Core takeaway: reformulate computation as bulk operations over columns instead of Python loops.

1-03_memory_management.ipynbMemory is part of algorithm design
  • GPU memory is finite, and intermediate results may briefly require much more memory than the final result.
  • Choosing the smallest valid integer or floating-point type reduces storage and can improve processing speed; lowering precision is a correctness decision, not merely an optimization.
  • Categorical types encode repeated labels compactly and can accelerate suitable operations.
  • Specifying columns and data types while loading avoids reading and converting data that the analysis never needs.

Core takeaway: estimate peak memory, choose types intentionally, and load only useful data.

1-04_interoperability.ipynbInteroperability in the GPU PyData ecosystem
  • CuPy brings a NumPy-like multidimensional array API to GPUs, while cuDF specializes in labeled, columnar tables.
  • GPU array standards such as the CUDA Array Interface allow libraries to share device data without costly host copies.
  • The latitude/longitude conversion illustrates how a NumPy-style numerical routine can move to CuPy and feed its results back into cuDF.
  • Boolean array indexing provides a common, vectorized selection pattern across array and DataFrame tools.

Core takeaway: choose the right abstraction for each operation while keeping data on device.

1-05_grouping.ipynbSplit, apply, combine
  • groupby splits rows by keys, applies computations to each group, and combines the results.
  • Built-in aggregations such as mean, count, and sum are usually more parallel and efficient than arbitrary group-wise functions.
  • Binning converts continuous values into analytically meaningful categories; bin boundaries encode assumptions that must fit the question.
  • agg returns summaries, transform broadcasts group results back to rows, and apply offers flexibility at a potential performance cost.
  • Pivot tables express multidimensional group summaries in a matrix layout.

Core takeaway: use the most structured group operation that expresses the analysis.

1-06_data_visualization.ipynbVisualizing data at scale
  • Chart choice follows the question: bars compare categories, histograms show distributions, scatterplots reveal relationships and clusters, and lines show ordered change.
  • Plotting every point in a very large dataset can be slow and visually misleading because of overplotting.
  • Datashader aggregates observations into display pixels, producing faithful images without sending every row to the browser.
  • cuxfilter links GPU-backed charts so interactions in one view filter the others.

Core takeaway: visualization is an aggregation problem as well as a rendering problem.

1-07_etl.ipynbExtract, transform, and load
  • ETL turns source data into a clean, typed, analysis-ready artifact: extract inputs, transform structure and values, then load the result.
  • Transformation includes filtering, coordinate conversion, feature creation, type conversion, and validation.
  • Parquet stores columnar data with metadata that enables column pruning and predicate-based skipping.
  • Persisting a well-designed intermediate dataset prevents downstream notebooks from repeating expensive preparation.

Core takeaway: optimize the reusable data product, not only the notebook that creates it.

1-08_cudf-polars.ipynbPolars lazy queries on the GPU
  • Polars offers eager execution for immediate results and lazy execution for building a query plan before computation.
  • A full lazy plan enables optimizations such as projection and predicate pushdown, reducing unnecessary reads and intermediate work.
  • The cuDF Polars engine examines the optimized plan and executes supported operations on the GPU.
  • The best acceleration path may be an execution-engine choice rather than a rewrite of the analytical logic.

Core takeaway: delaying execution gives the system room to optimize the entire query.

1-09_dask-cudf.ipynbScaling DataFrames with Dask-cuDF
  • Dask partitions data and represents operations as a lazy task graph coordinated by a scheduler and workers.
  • LocalCUDACluster assigns GPU workers; the dashboard exposes task progress, memory pressure, and bottlenecks.
  • compute() materializes a result, while persist() keeps reusable partitions distributed in worker memory.
  • Cluster setup should precede imports that create a CUDA context so computation does not bind prematurely to one device.

Core takeaway: distributed acceleration adds scheduling and partitioning concerns to ordinary DataFrame logic.

Section 2

Graph analytics

Road tables become graph structures whose topology and edge weights support reachability, travel-time, and centrality analysis.

2-00_introduction.ipynbEnvironment reset for graph work
  • The notebook revisits Jupyter execution, timing, GPU monitoring, and kernel lifecycle for a self-contained graph section.
  • Independent kernels make experiments reproducible but can retain GPU allocations until they are shut down.

Core takeaway: verify and reset computational state before starting a memory-intensive workflow.

2-01_section_overview.ipynbFrom tables to graph questions
  • The section moves from graph-ready data construction to cuGraph shortest paths and NetworkX-compatible accelerated centrality.
  • Graph analysis depends on both a correct topology and edge weights that represent the intended cost.

Core takeaway: graph algorithms are only as meaningful as the node, edge, and weight model supplied to them.

2-02_prep_graph.ipynbPreparing a weighted road graph
  • A graph requires compatible source and destination identifiers; reindexing maps external road-node IDs into a consistent graph ID space.
  • Road edges define connectivity, while node tables retain location attributes used for interpretation and visualization.
  • A distance-weighted graph answers shortest-distance questions. Converting road types to speeds and distance to travel seconds creates a time-weighted graph for fastest-route questions.
  • Merges are not clerical steps: join completeness and units determine whether weights are valid.

Core takeaway: topology defines what paths exist; edge weights define what “shortest” means.

2-03_cugraph.ipynbSingle-source shortest paths with cuGraph
  • A cuGraph graph is constructed from source, destination, and optional weight columns in a GPU DataFrame.
  • Single-source shortest path (SSSP) computes the minimum accumulated cost from one start node to every reachable node.
  • Changing the edge weight from road length to travel time changes the optimization objective without changing the topology.
  • Joining graph results back to node metadata makes abstract distances or times geographically interpretable.

Core takeaway: separate graph structure, cost definition, algorithm output, and real-world interpretation.

2-04_networkx_cugraph.ipynbcuGraph as a NetworkX backend
  • nx-cugraph accelerates supported NetworkX algorithms while preserving familiar NetworkX calls.
  • Backend selection can occur through an environment setting, an explicit backend argument, or type-based dispatch.
  • Centrality measures answer different questions: degree counts direct connectivity; betweenness identifies bridges; PageRank, eigenvector, and Katz incorporate the importance or reach of neighboring nodes in different ways.
  • Acceleration does not make centrality measures interchangeable; interpretation must match the mechanism of interest.

Core takeaway: separate the programming interface from the execution backend—and the metric from its interpretation.

Section 3

Machine learning and deployment

The section progresses from unsupervised spatial structure to prediction, validation, scalable training, and production inference.

3-00_introduction.ipynbEnvironment reset for machine learning
  • The recurring setup checks the GPU, times execution, and isolates notebook kernels before model training.
  • Model workflows often need extra memory for train/test copies, temporary arrays, and algorithm workspaces.

Core takeaway: resource headroom is part of a reliable training plan.

3-01_section_overview.ipynbThe accelerated ML workflow
  • The section covers clustering, regression, nearest-neighbor search, boosted trees, inference serving, and multi-GPU learning.
  • cuML mirrors familiar scikit-learn patterns, while XGBoost, Dask, and Triton extend the workflow across training scale and deployment.

Core takeaway: acceleration spans preparation, fitting, prediction, evaluation, and serving.

3-02_k-means.ipynbK-means clustering
  • K-means is an unsupervised algorithm that assigns observations to a chosen number of clusters by minimizing within-cluster distance to centroids.
  • The number of clusters is supplied in advance, so it encodes an analytical choice rather than a discovered truth.
  • Coordinate scale and distance geometry determine the meaning of proximity.
  • Visualizing labels and centroids helps diagnose whether the fitted partition is useful.

Core takeaway: K-means gives a compact partition, but its structure depends on k, scaling, and geometry.

3-03_dbscan.ipynbDensity-based clustering with DBSCAN
  • DBSCAN forms clusters from dense neighborhoods using a radius and a minimum-neighbor threshold.
  • It does not require a preset number of clusters and can label sparse observations as noise.
  • The radius has units inherited from the features, making coordinate choice and scale especially important.
  • DBSCAN can capture irregular shapes that centroid-based K-means may split poorly.

Core takeaway: DBSCAN defines clusters through local density, not distance to a global center.

3-04_logistic_regression.ipynbProbability, coefficients, and validation
  • Logistic regression models the probability of a binary outcome as a function of input features.
  • Coefficient signs describe conditional associations in the fitted model; they do not by themselves establish causation.
  • Grouping observed infection prevalence by age or sex provides a descriptive check against model interpretation.
  • A train/test split evaluates predictions on held-out observations and helps reveal overfitting.
  • Class imbalance means accuracy alone can be misleading; predicted risk should be compared with observed prevalence.

Core takeaway: interpretable coefficients still require held-out validation and cautious causal language.

3-05_knn.ipynbNearest-neighbor search
  • A nearest-neighbor model indexes reference coordinates, then returns distances and row indices for the closest references to each query.
  • Feature order and units must remain identical between fitting and querying.
  • The returned indices are mappings into the reference table; joining them to road-node metadata turns numerical neighbors into usable entities.
  • The hospital-to-road example is a spatial lookup task, not a classification model.

Core takeaway: nearest-neighbor results are only useful when distance geometry and index mapping are correct.

3-06_xgboost.ipynbGPU-accelerated gradient boosting
  • XGBoost combines many weak decision trees into a strong nonlinear predictor.
  • The objective defines the learning problem; binary:logistic produces infection probabilities, while the CUDA device setting selects GPU execution.
  • DMatrix is XGBoost’s optimized data representation, and cuDF data can remain on GPU through the training path.
  • Feature-importance scores and individual trees offer diagnostic views but are not causal explanations.
  • ROC curves and AUC summarize ranking performance across decision thresholds; a held-out test set is required for credible evaluation.

Core takeaway: faster nonlinear modeling does not remove the need for correct objectives, validation, and restrained interpretation.

3-07_triton.ipynbServing and measuring inference
  • Triton Inference Server decouples model serving from model training and supports multiple framework backends.
  • A versioned model repository and config.pbtxt declare the model artifact, inputs, outputs, batching, and backend.
  • Client/server predictions should be checked against local-model results before performance tuning.
  • Latency, throughput, batch size, and concurrency interact; raising concurrency can keep the server busy by overlapping communication and computation.
  • Perf Analyzer measures behavior, while Model Analyzer searches server configurations.

Core takeaway: production inference is a systems problem involving correctness, queues, batching, and resource use.

3-08_k-means_dask.ipynbMulti-GPU K-means with Dask
  • cuML’s Dask estimator distributes familiar K-means fitting across GPU workers.
  • Persisting coordinate partitions keeps repeatedly used training data resident across the cluster.
  • Calling fit triggers computation of the lazy workflow; predictions return distributed labels that can be filtered and aggregated.
  • Cluster centers must be interpreted by mapping generic output columns back to the original coordinate semantics.

Core takeaway: scaling an algorithm requires deliberate data placement and execution control, not only a distributed estimator.

Section 4

Integrated biodefense project

The final notebooks combine DataFrame operations, geospatial transformation, clustering, nearest neighbors, and grouped rates in a simulated epidemic. The scenario is pedagogical, not epidemiological evidence.

4-01_intro.ipynbFrom techniques to decisions
  • The project organizes three sequential questions: where infections cluster, which facilities are nearest, and which population characteristics are associated with higher infection rates.
  • Each task produces a small, machine-checked output from a larger analytical pipeline.
  • Kernel restarts between tasks protect limited GPU memory and reduce hidden state.

Core takeaway: an applied workflow must connect a decision question to reproducible transformations and a clearly defined output.

4-02_find_infected.ipynbFinding dense infection clusters
  • Load only needed fields, filter infected individuals, reset row indices, and convert latitude/longitude to planar grid coordinates.
  • DBSCAN identifies dense groups under explicit neighborhood-distance and minimum-membership assumptions.
  • Grouping cluster labels yields centroids and membership counts; the largest cluster is then selected.
  • A centroid summarizes a cluster’s center, not its full extent or uncertainty.

Core takeaway: the result depends jointly on preprocessing, coordinate geometry, DBSCAN parameters, and the summary chosen.

4-03_nearest_facilities.ipynbAssigning the nearest health facility
  • Hospital and clinic sources are cleaned, aligned to a common schema, concatenated, and converted to the same coordinate system as patients.
  • A nearest-neighbor index is fitted on facilities and queried with infected-person or new-patient coordinates.
  • Returned indices must be mapped back to facility identifiers; distances and coordinate spot-checks help validate the mapping.
  • Geometric proximity is a simplified proxy for access and does not account for roads, capacity, or travel conditions.

Core takeaway: shared geometry and correct index mapping make proximity queries valid; domain decisions may require richer costs.

4-04_identify_risk_factors.ipynbComparing infection rates across groups
  • Encoding infection as 0/1 makes the group mean equal to the infection proportion.
  • Rates, rather than raw case counts, permit comparison across employment groups of different sizes.
  • Joining employment codes turns category IDs into interpretable labels.
  • Grouping jointly by employment and sex probes whether an aggregate pattern differs within subgroups or may be confounded.
  • The exercise identifies associations in simulated data; it does not establish individual risk or causal effects.

Core takeaway: choose the correct denominator, inspect intersecting groups, and distinguish association from causation.
